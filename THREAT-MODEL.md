# lean-ftl Threat Model

Nov 1, 2026 · @Sebastien Riou

lean-ftl is assessed against two objectives, one for each way it can be deployed:

1. **On-chip or otherwise trusted NVM (Case 1).** The attacker can only send messages to the application and cut its power. lean-ftl must keep committed data atomic and fresh, must not let logical actions brick the device, and must never give access to unrelated RAM or flash, or code execution (objectives O1 to O4).
2. **External NVM (Case 2).** The attacker can also read and write the NVM at any time, and control its bus. lean-ftl does not protect the data then, but no NVM content or bus response may give access to the internal address space, or code execution (objective O5).

With the EWLF format of v0.4.0 and the large areas of v0.5.0, lean-ftl meets both objectives for regular, EWLF and large areas, within the assumptions below. NVM content only picks among fixed slot, record or log positions inside an area, API arguments are range-checked without overflow, an error aborts the transaction it interrupts, bad configurations are refused at registration, writes only program erased cells, the scan never erases, programs only words of zeros in a regular area on a flash declared with `zero_overwrite`, and programs nothing in an EWLF or a large area, where what it finds to repair is left to a call the application makes, and no version is ever erased before a complete newer one exists. What remains is by design or up to the integrator: `lftl_memread()` and write sources accept any pointer (T1.7), messages can drive wear-out (T1.5), `lftl_format()` is not anti-tearing (T1.6), an EWLF or a large area can be driven to refuse service by a run of power cuts each inside the same short window, which it reports before it happens (T1.14), a large area refuses an update larger than the free units of its pool (T1.15), flash with ECC needs an NMI handler that lets a read of a torn word complete (T1.13), and external NVM needs a careful driver and careful parsing (T2.3 to T2.8).

Findings are removed from this document once fixed, as in ISSUES.md; git history keeps them, including LF-1 to LF-12, which some test comments still name, and LFTL-001 to LFTL-013, the last three closed by the read-only scan described on the [anti-tearing page](https://lean-ftl.readthedocs.io/en/latest/design.html) of the documentation. No finding is open.

## Scope and system overview

This model covers the core library, `liblean-ftl/source/ftl.c`, `liblean-ftl/source/ftl_internal.h` and `liblean-ftl/include/lean-ftl.h`, with the EWLF format of v0.4.0 and the large areas of v0.5.0, as integrated on a bare-metal MCU. Example code, the reference callbacks under `target/` and the test harnesses are out of scope, except where the integrator contract depends on them.

How lean-ftl works, as far as security is concerned:

- An **area** is split into `n_slots = area_size / slot_size` slots. One slot holds the current data; the next one is erased and rewritten on every update.
- Each slot ends with 3 write units of metadata: `version`, `checksum` and `checksum2`. The checksum is a 32-bit CRC over the data plus the version (the CRC32C core with the reciprocal form of its polynomial, effectively 27 bits, ISSUES.md LFTL-014; the format of regular areas is frozen).
- On first access, `find_current_slot()` scans all slots, skips erased versions (`0xFFFFFFFF`) and slots failing the checksum, and picks the highest version. `ctx->data` is set from the **loop index**, not from NVM content. If that slot's `checksum2` mismatches, the whole `checksum2` write unit decides, on one reading: partially programmed means the checksum is complete, and the slot is taken, its `checksum2` unit pinned to zeros first on a flash declared with `zero_overwrite`; all erased means the cut came during the checksum word at the latest, which may be weakly programmed, and the previous version is current: the scan runs again without the torn slot, which is tombstoned first (its version item pinned to zeros) on a flash with `zero_overwrite` and left as it is otherwise. The scan never erases and never copies a slot; the next write erases the torn slot, as every write erases its target.
- An **EWLF area** (`lftl_register_area_ewlf()`) is 2 to 256 **data units** followed by 2 **log units**, each one erase unit. A data unit packs many **records**: a start marker (an all-zero write unit, programmed first), the data, then a meta field (the 32-bit `version` and a 64-bit checksum, CRC-64/NVME over the version then the data, in one program). A log unit holds **pairs**, regular then reserved, then **certificates**: a pair is a marker (all zeros), an entry (the generation of its log unit, the data unit and the position of a record, the record's version, a CRC-64/NVME of those) and a confirm (all zeros), each programmed only after the one before it returned; a certificate is an all-zero write unit that records that the erase of the other log unit returned. The current record is the one named by the newest valid entry of the live log unit. A write programs a record at the first position of the current record's unit above the started ones, then the pair that names it; when the data unit is full the next one is erased first, whatever it reads, never the unit of the current record; when the log unit has no regular position left the log switches: the other log unit is erased, a certificate programmed, and the entry goes there. A program the flash refuses (`LFTL_NVM_STATUS_REFUSED`) is stepped over. EWLF areas have no transactions.
- On first access to an EWLF area, `ewlf_scan()` reads the two log units, once, and only at pair and certificate positions, then checks the one record the newest valid entry names. It programs and erases nothing. When that entry is proven by its confirm, nothing is started above it and the other log unit holds no possible first entry of the next generation, the record is current. Otherwise a repair is pending: `lftl_read()` and the write functions raise `LFTL_ERROR_SCAN_PENDING` until the application calls `lftl_complete_scan()`, which programs a copy of that entry above everything started, one pair, by a log switch when the live unit has no position left, and only then shows the record. `lftl_scan_status()` reports the pending repair and how many badly placed power cuts the area can still take; `lftl_read_unproven()` reads the record the scan chose in any state. `ctx->data` is set from the position the entry names, checked against the configured layout: NVM content picks among fixed positions inside the area, but never sets where a record starts.
- The application addresses data through **logical addresses** inside the `nvm` struct (`nvm.data0`). `translate_addr()` maps them to the current slot or record after an overflow-safe range check, and the transaction functions run the same check first.
- Transactions (regular areas only) use a caller-owned RAM bitmap (`transaction_tracker`, one bit per write unit) to detect double writes and to know which units to copy at commit.
- A **large area** (`lftl_register_area_large()`) is a **pool** of erase units followed by the 2 log units of an EWLF area. Its data is cut into **chunks** of one erase unit each, a pool unit holding one chunk and nothing else. The data of a log pair is a **map**: the pool unit of each chunk (16 bits, `0xFFFF` for a chunk never written), the unit filled last, and the CRC-64/NVME of the whole data; the pair is a marker, the map, a meta field (generation, version, and a CRC-64/NVME of the map and of those) and a confirm, each programmed after the one before it returned. A write takes, for each chunk it touches, the next pool unit that holds no chunk of the current map nor of the open transaction, erases it whatever it reads, programs the chunk, then commits the new map as an EWLF area commits an entry. The scan is that of an EWLF area; a pair is valid only when every unit its map names lies in the pool. The data is checked against its CRC once per reset, by `lftl_check_data()` or before its first use, never by the scan. Transactions take a free unit per chunk they touch and erase nothing at their start.
- `lftl_register_area()`, `lftl_register_area_ewlf()` and `lftl_register_area_large()` check the configuration (write unit size, area bounds and alignment, slot count, EWLF record size, data unit count, pool size and log room) and raise `LFTL_ERROR_BAD_CONFIG` before linking a bad area. `LFTL_AREA` and `LFTL_AREA_EWLF` reserve the pages the run-time layout needs, and `LFTL_AREA_EWLF` refuses at compile time a record that does not fit twice in a page. An EWLF area written by an earlier version reads as `NO_VALID_VERSION` and must be formatted again.
- NVM access goes through integrator callbacks (`erase`, `write`, `read`), set once per NVM in `lftl_nvm_props_t`. The exception is `mem_read()`, which copies any address outside every registered NVM with `memcpy`; that is how RAM `src` buffers are read. Errors go to the NVM's `error_handler`, after the transaction of the area the failing operation was for is aborted. The handler must not return; if it does, the library loops forever.

| Asset | Why it matters | Case 1 | Case 2 |
| --- | --- | --- | --- |
| Internal RAM and the CPU's address space | Corruption leads to code execution or secret disclosure | Protect | Protect (sole objective) |
| Firmware and other non-LFTL flash | Erasing or overwriting it bricks the device or plants code | Protect | Protect |
| Integrity of committed LFTL data | Application state, counters, configuration | Protect | Not protected |
| Freshness (no rollback to an older version) | Anti-replay counters, revocation state | Protect | Not protected |
| Availability of the area | Device must keep booting | Protect against logical attacks | Not protected |
| Confidentiality of LFTL data | Secrets stored in NVM | Out of scope (no physical access) | Not protected |

## Assumptions and out of scope

Both cases rest on the same baseline: the code, the configuration and the callbacks are trusted; only runtime inputs are hostile.

**Assumed in both cases**

- Firmware, the lean-ftl configuration (`lftl_nvm_props_t`, every `lftl_ctx_t`) and the callbacks are trusted and correct. `write_size`, `erase_size`, `area` and `data_size` are compile-time constants, never derived at runtime from the NVM (for example from SFDP tables). Registration checks that the configuration is consistent, but cannot tell whether it matches the hardware.
- The flash behaves as stated on the [Flash requirements and assumptions](https://lean-ftl.readthedocs.io/en/latest/flash.html) page: requirements R1 to R8, and the tearing model T1 to T5 the anti-tearing argument below rests on (a cut affects only the unit being written; a weak word may read anything, and may read all erased later).
- `error_handler` never returns: it resets, or `longjmp`s to a recovery point. The library loops forever if it does return, so a returning handler costs availability instead of turning each check into a no-op.
- An error aborts the transaction of the area it happened on, and only that one.
- lean-ftl is called from one execution context per area. It is not thread-safe or reentrant, and its registration lists (`first_area`, `first_area_ewlf`, `first_nvm`) are global.
- Power loss or reset at any instant is **in scope**. It is the normal operating condition the anti-tearing logic is built for, not an attack. Deliberate glitching that corrupts a single instruction or flash cell is fault injection and stays out of scope.

**Out of scope in both cases**

- Fault injection: voltage, clock, EM or laser glitches.
- Side channels: power, EM, timing, cache. One choice of the build bears on them: the CRC-64 of EWLF and large areas reads a table of 16 entries at an index that depends on the data, and a library built with `LFTL_CRC64_BITWISE` computes it bit by bit, without a table.
- Physical readout of internal flash or RAM (decapping, probing, debug port).
- Bugs in application code that do not go through the lean-ftl API.

**What the attacker controls**

|  | Case 1: on-chip / trusted NVM | Case 2: external NVM |
| --- | --- | --- |
| Messages to the application | Yes, arbitrary content and timing | Yes |
| Arguments the application derives from messages (offsets, sizes, sequences of calls) | Yes, insofar as the application lets them through | Yes |
| Power cuts at chosen instants | Yes (functional, not fault injection) | Yes |
| NVM content | No | Yes, read and write at any time, including between two reads |
| NVM bus responses (status, errors, timing) | No | Yes |

## Case 1: on-chip / trusted NVM

The transaction and anti-rollback logic holds against power cuts for both kinds of area, and so does the memory-safety objective. Out-of-range arguments end in the error handler before any access, an error ends the transaction it interrupts, and configurations that would overflow buffers or write outside the area are refused.

The attacker can only send messages to the application. They reach lean-ftl through the arguments the application derives from those messages (`dst_nvm_addr`, `src`, `size`), through the sequence of calls (start, write, commit, abort, duplicates), through the content of data the application stores for them, and through the timing of power cuts. lean-ftl is the last line of defence: its documented checks (`FIRST_NOT_IN_DATA`, `LAST_NOT_IN_DATA`, `TRANSACTION_OVERWRITE`) are expected to stop an application bug that forwards a bad offset or a duplicated record.

### Security objectives

| Objective | Status | Basis |
| --- | --- | --- |
| O1. Atomicity: after any power cut, reads return either the old or the new committed data | Holds | Regular areas: writes go to the erased next slot; metadata is written last, `checksum2` after `version` and `checksum`. A torn slot fails CRC32C and is skipped. A slot whose `checksum2` reads all erased is not taken when another slot is valid (its checksum may be weakly programmed, and no boot ever returned it); one whose `checksum2` is partially programmed is taken (its checksum is complete). The scan never erases; the next write erases the torn slot, with 2 slots as with more. EWLF areas: a record is written start marker first, then data, then the meta field, only into a unit erased right before its first record, and its checksum is computed from the data meant to be written; the pair that names it follows, marker, entry, confirm. A record no entry names is never read as one; an entry that does not read valid is not taken; one that reads valid is taken, after a copy of it when its confirm does not read all zeros. A torn rollover leaves its record in a unit the next rollover erases again before programming it (LFTL-013). Only pair positions are read as entries and only named positions as records, so data cannot pass for either. Large areas: a chunk is programmed into a pool unit erased right before, and the map that names it is committed only after every chunk's program returned; a chunk no map names is never read; the commit is that of an EWLF area. Detection of a torn data write is probabilistic (regular areas 2^-27, EWLF and large areas CRC-64 2^-64). |
| O2. No rollback below the last committed version | Holds; residuals listed | `version` is incremented on every commit and the highest valid version wins, in regular and EWLF areas alike. Wrap at `0xFFFFFFFE` needs about 4.3 billion updates, far beyond endurance (native endurance × wear-leveling factor). An interrupted write can bring back the previous version, never an older one. Regular areas: on a flash declared with `zero_overwrite` the scan pins what it decides about the one word a power cut can leave weak, so no later boot decides otherwise; without it (the W25Q32RV, the M5531 until measured, the CH32V307) the decision is made again at every boot on the word as it reads then, until the next write, a rollback or a late new by one version; and one timing case rests on T3. EWLF areas: a version once shown is never taken back, a write that was cut is never shown after an older version was, and nothing is lost, with any number of power cuts and without T3: a record is shown only when its entry is proven by a confirm programmed after it, or after a copy of the entry whose three programs returned in that boot, above everything a cut may have left, and a log unit is written only after an erase and a certificate that the same session saw return. The design is checked exhaustively on a model up to 4 power cuts and 8 boots, and rests on two properties of the flash beyond the tearing model, one of them measured on the STM32U5 ([how the design was checked](https://lean-ftl.readthedocs.io/en/latest/design.html#design-ewlf-checked)). What remains is not a rollback but the stuck state, T1.14. Large areas inherit this from their log, whose pairs hold the map: no pool unit is erased while it holds a chunk of the current map, of the map being committed or of the open transaction, and nothing is erased while a repair is pending; the pool rules are model checked with the log ([how](https://lean-ftl.readthedocs.io/en/latest/design.html#design-large-checked)). |
| O3. No bricking through logical actions | Partly | Wear-out, a torn `lftl_format` and, on flash with ECC, a torn write without the NMI handling of T1.13 can leave the device unusable, and a run of power cuts each inside the same short window can leave an EWLF or a large area refusing service until it is formatted; see threats T1.5, T1.6, T1.13 and T1.14. A large area whose data the flash changed refuses to use it until the application repairs it, T1.16. |
| O4. No access to unrelated RAM or flash, no code execution | Holds | Given the integrator contract below, T1.7 in particular: arguments are range-checked before any access, metadata buffers are sized from the write unit, an aborted transaction leaves no tracker behind, and every slot or record the library touches lies inside its area. |
| O5. Bounded time, independent of the NVM state after boot | Holds for regular areas; EWLF areas bounded only | Every loop runs over a configuration constant (`n_slots`, `n_pages`, `records_per_unit`, the two passes of `find_current_slot()`, the pair and certificate positions of `ewlf_scan()`), and the callbacks complete or fail (R5 of the flash page), so each operation has a worst case that follows from the configuration alone. After the scan, a regular-area write costs one slot erase plus the data and the meta-data whatever the NVM holds: it erases its slot unconditionally (`write_core()`, `erase()`, transaction start). An EWLF write is bounded but depends on the state: started positions left by cut writes are stepped over, in the data unit and in the log unit, a unit's worth at most; a rollover is exactly one erase in every state, and a log switch one erase and at most two more pairs. The scan of a regular area is bounded but state-dependent by design: up to two passes with a CRC per slot whose version is at least the running maximum. The scan of an EWLF area reads its two log units whole and checks one record, the same work in every state; the repair it may leave pending is one pair, or a log switch. A large area's scan reads its two log units whole; a write costs, per chunk it touches, one erase and the chunk, in every state, plus searches of the free units that read the map, bounded by the pool size times the number of chunks; the check of its data reads all of it, once per reset. No test measures timing. |

### Threats

| ID | Threat | Mitigation in lean-ftl | Residual risk |
| --- | --- | --- | --- |
| T1.1 | Out-of-range destination or size reaches a write | Overflow-safe range check (`check_in_data()`) before the tracker or any NVM access | None |
| T1.2 | Out-of-range source or size reaches a read | Same check in `lftl_read()` and `lftl_transaction_read()` | None |
| T1.3 | Error raised mid-transaction leaves stale state | The error aborts the area's transaction before the handler runs | An error on another area leaves this area's transaction open. If the handler unwinds the frame holding its tracker, the recovery path must abort it. |
| T1.4 | Reading uncommitted data and acting on it | `lftl_read()` returns committed data during a transaction | Application must not base security decisions on `lftl_read_newer()` or `lftl_transaction_read()` results; the transaction may still abort. |
| T1.5 | Wear-out driven by messages | None | Each `lftl_basic_write()` to a regular area erases a full slot, and so does each `lftl_transaction_start()`, even if aborted. A loop of start/abort burns endurance. EWLF areas erase one data unit per unit's worth of records and one log unit per log unit's worth of updates; a boot programs nothing unless the application asks for the repair, one pair. A large area erases one pool unit per chunk an update or a transaction touches, aborted or not, and one log unit per log unit's worth of commits. The application must rate-limit or batch writes. |
| T1.6 | Power cut during `lftl_format()` | Documented as not anti-tearing | The next scan raises `NO_VALID_VERSION` on every boot. The application must keep its own "formatted" flag in another area and recover. |
| T1.7 | Arbitrary-pointer gadgets | None, by design | `lftl_memread()` copies from any address, and the `src` of every write may be any address. An attacker-controlled pointer reaching either one reads arbitrary memory, or copies it into NVM to read back later. Only pass pointers the application built itself. |
| T1.8 | Stale data after logical erase | Documented | `lftl_erase_all()` leaves previous versions in other slots, and in EWLF areas, older records stay until their erase unit is recycled; in large areas, older chunks stay until the head reaches their unit. Any raw NVM read (for example `lftl_memread()` outside the area) can still return them. |
| T1.9 | First operation on an area after a reset | `translate_addr()` and `lftl_transaction_start()` locate the current slot on first use | None |
| T1.10 | Power cut during an EWLF write | A data unit is erased right before its first record; a record torn before its pair is named by no entry and is stepped over; a pair torn in its marker or in an entry that reads invalid is buried under a copy of the previous decision; one torn after an entry that reads valid is made solid by a copy before it is shown; a torn rollover or log switch is redone, erase included | None against the data; the stuck state, T1.14 |
| T1.11 | Attacker-chosen data stored in an EWLF area | Only the pair positions of the two log units are read as entries, and only the positions they name as records, so data cannot pass for either | None |
| T1.12 | Configuration that does not fit the run-time layout | Registration checks the configuration; `LFTL_AREA_EWLF` refuses an oversized record at compile time and reserves the two log units | None for what registration can see; whether the configuration matches the hardware stays an assumption |
| T1.13 | Torn program or erase on flash with ECC | None: the scan and EWLF writes must read a word before they can decide on it; in a regular area, with `zero_overwrite`, the pin or tombstone that follows programs a valid codeword over the torn word; in an EWLF area the torn word stays where it is and is read at every boot until its unit is erased | On STM32L5 and STM32U5 a double-bit ECC error raises an NMI on read, and a torn program or erase can leave such a word. The NMI handler must clear the error and return, so the read completes and lean-ftl decides on the content; one that loops or resets hangs the device at every boot. The torn word is never in committed data. With `zero_overwrite`, which both parts declare, the word is pinned at the first boot that reads it, one NMI in all, provided the check bits of an all-zero word are all zero: inferred from the documented all-zero overwrite, to be measured (FLASH.md). A cut during the pin itself can leave the data cells at zero and a check cell weak, an NMI per boot until the unit is erased. For an EWLF area the read callback must also return, for the word that faulted, a value that is neither all erased nor all zeros, so that the word counts as started and proves nothing. See the integrator section, and R7 and T5 of the [flash page](https://lean-ftl.readthedocs.io/en/latest/flash.html#flash-tearing). |
| T1.14 | An EWLF or a large area driven to the stuck state by power cuts | The area refuses to write, or to show a version it cannot prove, only after a reserve is exhausted: as many log switch attempts as it has certificates (32 by default, an area parameter), each cut inside the same 256 us window, or as many cut repairs as a log unit has positions. `lftl_scan_status()` reports the number of such cuts left, so that the application can stop and ask for a stable power supply before it writes or repairs | Loss of availability, never of data nor a rollback: the content stays readable with `lftl_read_unproven()` and `lftl_format()` brings the area back empty. An attacker who controls the power and can time it to a fraction of a millisecond can get there; with the application's threshold in place, only with the user's consent for the last attempts |

| T1.15 | A large area short of room | An update or a transaction that touches more chunks than the pool has free units raises `LFTL_ERROR_LARGE_NO_SPACE` before anything is programmed or erased; a transaction is aborted | Availability for that update only. A pool of the chunks plus the chunks of the largest update or transaction never lacks room, whatever the power cuts; the integrator sizes it ([sizing](https://lean-ftl.readthedocs.io/en/latest/using.html#large-areas)) |
| T1.16 | Data of a large area that the flash changes after it was written | The CRC-64 of the whole data, checked once per reset, before the first use of the data or when the application asks (`lftl_check_data()`). A mismatch raises `LFTL_ERROR_DATA_CHECKSUM` at every use, never falls back to older data | The application decides: `lftl_read_unchecked()` reads what is still right, `lftl_repair_checksum()` accepts the data as it reads, a write of the whole data or `lftl_erase_all()` makes the area sound. Changes after the check, in the same session, are not seen until the next reset. Regular and EWLF areas check their data at their scan only, the same way |

## Case 2: external NVM

The library's own handling of hostile NVM content meets the objective for both kinds of area: NVM content only picks among fixed slot or record positions inside the area, and never sets an address, index or size. A bus error inside a transaction aborts that transaction (T2.2). The integrator's driver and application parsing carry the remaining risk.

The attacker reads and writes the external NVM at any time, including between two reads made by the same function, and controls every bus response. Integrity, freshness, confidentiality and availability of LFTL data are explicitly **not** goals. The only objective is:

> **O5.** No sequence of NVM contents or bus responses gives the attacker read or write access to the internal address space, or code execution.

### What the library reads from NVM, and what it does with it

| Value read from NVM | Used for | Can it become an address, index or size? | What the attacker can do with it |
| --- | --- | --- | --- |
| `version` (per slot or record) | Choosing the current slot; matching an EWLF record with the entry that names it; `+1` for the next version | No. The slot index or record position comes from the scan loops, so `ctx->data` always points at a slot or record of the configured area | Pick any slot or record; force `VERSION_COLLISION`; force `NO_VALID_VERSION`. Setting `0xFFFFFFFE` makes the next commit write `0xFFFFFFFF`, which the next scan treats as erased |
| `checksum` | Slot or record validity check | No | Forge freely; neither CRC is keyed |
| `checksum2` | Detecting a torn metadata write, in slots | No | With it erased or partially programmed on a valid slot: force one word program at the next boot on a flash with `zero_overwrite` (a pin or a tombstone, once per crafted word, since a pinned word reads zeros for good); nothing without |
| EWLF log entry | Choosing the current record: the newest valid entry of the log unit of the higher generation | No. The data unit and the position it names are checked against the configured layout, and the record it names against its version and checksum | Pick any record whose checksum the attacker can compute; force `NO_VALID_VERSION`; force a pending repair, one pair once the application asks for it |
| EWLF markers, confirms and certificates | Telling a started position, a proven entry, a log unit that may be written without an erase | No. Only pair and certificate positions of the two log units are read | Force a pending repair at every boot; force the next write to switch the log, one erase; exhaust the positions or the certificates of a log unit, the stuck state, which `lftl_format()` clears |
| EWLF start marker | Choosing where the next record goes | No. The write path only steps over positions of the current record's unit | Force the next write to step over positions, at most a unit's worth, and to roll over, one erase |
| Data bytes | Copied slot to slot at commit, copied to caller buffers | No. Copy sizes come from the configuration or the caller | Any content, changed between reads |
| Callback status codes | Raising `LOW_LEVEL_*` errors | No | Raise an error inside any operation, at a chosen point; it aborts that area's transaction |

The library may read the same metadata more than once during a scan (a unit's key, then its records; the cross-check build reads everything twice). A time-of-check/time-of-use (TOCTOU) change between those reads only changes which data is returned. That is a data-integrity effect, which is accepted.

### Threats

| ID | Threat | Status | Required mitigation |
| --- | --- | --- | --- |
| T2.1 | Hostile metadata forces an error path | Availability only | The library loops forever if the handler returns, so `NO_VALID_VERSION` cannot produce a wild pointer. The handler must still reset or `longjmp`; one that returns hangs the device. |
| T2.2 | Bus error inside a transaction | Mitigated | The error aborts that area's transaction before the handler runs. See T1.3 for transactions on other areas. |
| T2.3 | Application parses NVM data as trusted | Integrator | Treat every byte read from an external area as an untrusted packet: bound every length and index against compile-time constants, store no pointers or function pointers, and validate enums and state values. |
| T2.4 | Double fetch by the application | Integrator | Read once into RAM with `lftl_read()`, validate the RAM copy and use only that copy. Never read a length field and then the payload in two calls, and never dereference the `nvm` struct directly. |
| T2.5 | Driver trusts the device | Integrator | Translate each virtual address to a device offset with a bounds check against the window. Never take sizes from the device (SFDP geometry, length fields). Bound every busy-wait loop with a timeout. |
| T2.6 | Write callback dereferences a virtual address | Integrator | lean-ftl copies slot to slot, so the write callback's `src` may lie inside the NVM window. For SPI flash that is not memory-mapped, the callback must read it through the device into a bounce buffer, never as a RAM pointer. |
| T2.7 | Virtual window overlaps real memory | Integrator | `nvm_props.base` and `size` decide whether an address goes to the callback or to `memcpy`. Place the window in unmapped address space so a stray dereference faults, and keep it apart from RAM, peripherals and internal flash. |
| T2.8 | Memory-mapped external flash (XIP, OctoSPI) | Integrator | Content can change between two CPU loads. Mark the region non-executable in the MPU, and make the bus-fault handler reset rather than resume. |
| T2.9 | Forced reformat or wear | Accepted | If the "formatted" flag lives in external NVM, or the application reformats on `NO_VALID_VERSION`, the attacker can wipe the data. `lftl_format()` erases a range taken from the configuration, so this path stays memory-safe. |
| T2.10 | Hostile EWLF content | Mitigated | Only pair and certificate positions of the log units and the record position an entry names are read, each within its erase unit and checked against the configured layout, so the scan never reads past the area. Crafted content can make the area refuse service (the stuck state), never more. |
| T2.11 | Hostile large-area content | Mitigated | The log is read as for an EWLF area; a pair is valid only when every unit its map names lies in the pool, so reads and erases stay in the area. Crafted content with a valid CRC can name any pool unit for any chunk, two chunks the same unit, or a wrong checksum of the data: wrong data, `LFTL_ERROR_DATA_CHECKSUM`, `LFTL_ERROR_LARGE_NO_SPACE`, or the stuck state, never an access outside the area. |

## Integrator responsibilities and hardening

The library cannot check the contract below itself. Each item is needed in both cases unless marked.

**Contract checklist**

- [ ] `error_handler` never returns: it resets, or `longjmp`s to a recovery point. One that returns hangs the device.
- [ ] A transaction tracker is at least `LFTL_TRANSACTION_TRACKER_SIZE(ctx)` bytes, and stays valid until the transaction ends with `lftl_transaction_commit()` or `lftl_transaction_abort()`. A tracker in static storage always does. One on the stack needs its transaction ended before that frame returns, or is unwound by an error handler, including for an error on another area: lean-ftl aborts only the transaction of the area an error happened on.
- [ ] Before calling lean-ftl, the application checks every offset and size it derived from a message against the field it targets, overflow-safe: `off <= field_size && len <= field_size - off`. lean-ftl raises an error instead of corrupting memory, but with a handler that resets, each bad message would become a reboot.
- [ ] Batch messages are de-duplicated before a transaction, so `TRANSACTION_OVERWRITE`, which aborts the transaction, cannot be triggered from outside.
- [ ] No attacker-influenced pointer reaches `lftl_memread()` or the `src` of any write (T1.7).
- [ ] Message-driven writes are rate-limited and batched against the endurance budget: native endurance × wear-leveling factor per page (T1.5).
- [ ] `zero_overwrite` is declared only for a flash whose manual documents programming all zeros over a programmed word (STM32L5, STM32U5), and left false otherwise: lean-ftl then never programs a unit that is not erased, and the scan writes nothing (N3 of the flash page).
- [ ] A "formatted" flag in a separate area lets the application recover from a torn `lftl_format()` (T1.6).
- [ ] Flash with ECC (STM32L5, STM32U5 and similar): the NMI handler clears the double-error flag and returns, so a word left by a torn program or erase reads as content lean-ftl then rejects, instead of hanging or resetting the device at every boot (T1.13). The write unit is at least the ECC codeword, so that each metadata item of a slot, and each flag of a record, is its own codeword (16 bytes on the STM32U5, 8 on the L5). R7 of the [flash page](https://lean-ftl.readthedocs.io/en/latest/flash.html#flash-required).
- [ ] Case 2 only: the driver, the address window and the application parsing follow T2.3 to T2.8.

**Defence in depth: bound the callbacks.** The callbacks check that each range is a flash address. The reference `erase`, `write` and `read` callbacks do: the STM32 ones refuse anything outside the flash, and the CH32V307 one also accepts the flash's `0x00000000` alias. They cannot check that a range is inside an LFTL area, since they do not know where the areas are. An integrator who knows its layout can bound its own callbacks to the LFTL areas, which turns a future bug that reaches other flash into an error. On parts with an MPU or TrustZone, also make the LFTL areas non-executable, and make firmware flash write-protected while lean-ftl runs.

**Flash with ECC (STM32L5, STM32U5 and similar).** These parts protect each flash word with an ECC: a single-bit error is corrected on read, a double-bit error sets `ECCD` in `FLASH_ECCR`, records the address, and raises an NMI. A program or erase interrupted by a power cut can leave a word whose data and ECC do not match, and lean-ftl must read such words before it can judge them: at the first access after a reset, the scan reads the version word of every slot of a regular area and every word of the two log units of an EWLF or a large area, and an EWLF write reads the start markers of the current record's unit to find a free position. The torn word always lies in the slot being erased or written, or in the record being written, never in committed data, so lean-ftl's own checks (version, checksum, entry CRC, erased state) reject it or step over it once the read completes, as they do on parts without ECC and on the Linux simulator, where the read returns the raw content directly. The reference STM32 callbacks read with `memcpy` and do nothing about ECC, and the testbenches' generated NMI handlers loop forever: there, a torn write hangs the device at every boot until the area is reformatted from outside. The integrator's NMI handler must check `ECCD`, clear it and return, so that the read completes; the recorded address can be logged. It must not reset, which turns every boot into the same failure, and must not erase anything: the torn EWLF word lies in the erase unit that holds the current record or in the live log unit. For an EWLF or a large area the read callback must also return, for the word that faulted, a value that is neither all erased nor all zeros.

**If Case 2 needs integrity or freshness after all.** lean-ftl cannot provide either, but it composes with a small wrapper:

1. Encrypt and authenticate each record with an AEAD (for example AES-GCM or ChaCha20-Poly1305), with a key kept on chip.
2. Bind the associated data to the area identifier and a record version, so records cannot be swapped between areas or fields.
3. Keep the version counter in an **internal** lean-ftl area, which is Case 1 storage, to detect rollback of the external copy.
4. Verify the tag over the RAM copy (T2.4) before parsing anything.

This is the same pattern TF-M Protected Storage uses over its internal trusted storage.

## Verification plan

`testit` runs the test suite on the Linux NVM simulator, whose write callback refuses to program a write unit that is not erased, like STM32U5-class flash. Most tests run under the tearing simulation, which cuts power at every write-unit boundary and checks, at two boots in a row, that the data reads back as the last or the previous committed version and never as the previous one after the last was read, a rollback; test 35 checks the simulator itself: a cut anywhere in a multi-unit write or erase corrupts exactly the bytes past it in the regular areas, and in the EWLF areas leaves the unit it lands in weak, reading differently at every read (T2 of the flash page without T3), the units after it untouched. When the boots that recover from a cut program anything, the same cut is run again with a second cut at each of those programs. After each tear and that check, the sweep writes new data to every area it checks and checks again after another simulated reset, so the first write after a power cut is covered too. Tests 24, 29, 32, 33, 34 and 36 build specific torn states by hand, regular and EWLF: a slot whose `checksum2` is erased or partially programmed, pinned or tombstoned where the flash allows it (test 24), a next slot whose version word reads as the current version after a torn erase (test 32), an EWLF update cut after each of the words it programs, with what the scan reports, refuses and then repairs (test 33), a power cut during the scan's tombstone, which must leave the previous version untouched and erase nothing (test 34), power cuts in EWLF writes and rollovers (test 29), and three cycles of writes over an area of 26 data units with cuts at every program of an update, during a rollover's erase, and the log switches the writes bring (test 36). Test 37 rebuilds areas formatted and written by lean-ftl v0.1.0 and checks that the scan takes the slot v0.1.0 had current and programs and erases nothing, before the area takes new writes. Test 38 checks the CRC-64 against its published value and forges an update with it, record and pair. Tests 39 and 40 drive EWLF areas through the sequences of cuts and scripted weak readings the argument rests on (a weak confirm and a weak entry read one way then the other, a first entry of a log switch that a boot can see, the sequence the certificates exist for, the stuck state after exactly as many cuts as certificates) and through random writes, cuts, boots and cut repairs on two geometries, checking after every boot that the data shown is never older than data already shown nor a cut write that an older version was shown after. The suite runs twice, with the simulator's all-zero overwrite and `zero_overwrite` on, then off (`--no-pinning`), with weak words in the EWLF areas both times. Tests 41 and 42 write a large area in every shape, plainly and in transactions, under the same sweep, which also checks the large area after every cut of every test; test 43 checks its configuration, the room of its pool, the head going round and its transaction rules; test 44 loses a chunk behind the library's back and checks the lazy check, the unchecked read and the repair of the checksum; test 45 is test 40 for a large area. The design of EWLF and large areas is checked apart from the code, by the exhaustive model checker of `test/ewlf-model`.

`testit` also runs `test/asan/build-and-run`, which builds `test/asan/asan_harness.c` with AddressSanitizer and UndefinedBehaviorSanitizer. The harness covers hand-built scenarios: out-of-range arguments, an error inside a transaction, write units larger than 16 bytes, a transaction started first after a reset, power cuts in EWLF writes on NOR and STM32U5-like flash, hostile EWLF content, an oversized EWLF record, every call on a large area, a large-area map naming a unit past the pool, and a large-area read whose size wraps. Each test must end without a sanitizer report or a callback access outside the area, and with its expected result.

On 2026-10-31 the suite at v0.2.0 ran on the NUCLEO-U5A5ZJ-Q and NUCLEO-L552ZE-Q boards (through lean-hwbridge, the test firmware built with `HAS_PRINTF`): tests 1 to 37 passed on both, in the pinning variant their builds declare, so the pins and tombstones of the scan have been programmed over partially programmed words on real STM32 flash, through callbacks that check the flash's error flags. On 2026-11-03 the suite with the EWLF format of v0.3.0 (commit 760da0c) ran the same way: tests 1 to 40 passed on both boards. Test 33 writes the four torn record states by hand, so the scan's tombstone and its copy of a half-written record have run on real STM32 flash; tests 35, 39 and 40 need the simulator and are empty on a board, so the stuck-state pin and the weak-word model have not. On 2026-11-15 the suite with the EWLF format of v0.4.0 (branch `ewlf-no-rollback`) passed tests 1 to 40 on the NUCLEO-U5A5ZJ-Q and on the NUCLEO-L552ZE-Q; test 33 writes by hand an update cut after each of its words, so the scan, the pending repair and the repair have run on real STM32 flash. The day before, on the same board, an erase interrupted by a system reset left an already erased page cleanly erased 40 times out of 40, which the EWLF design relies on (`FLASH.md`, section 4, point 5). On 2026-11-22 the suite with large areas (branch `chunked-area`, commit cd3d0fa) passed tests 1 to 45 on the NUCLEO-U5A5ZJ-Q and on the NUCLEO-L552ZE-Q: tests 41 to 44 format, write, read and check a large area on real flash, transactions and the loss of a chunk included; test 45, the stress under the weak word model, needs the simulator and is empty on a board. A board run does not produce a torn program, which only a power cut during one does.

Not covered: the ECC behaviour of real flash (T1.13). The simulator returns the raw content of a torn word; the NMI handling is the integrator's, and a power cut during a program or erase on an STM32L5 or STM32U5 board would be the test for it.

Three fuzzing harnesses would widen the coverage beyond these scenarios:

| Harness | Covers | Inputs | Pass criterion |
| --- | --- | --- | --- |
| API sequence fuzzer (libFuzzer) | Case 1, O4 | Random sequences of start, write, write\_any, read, read\_newer, commit, abort, erase\_all, with random offsets and sizes, on regular and EWLF areas, including sequences that begin right after a reset; the handler `longjmp`s and recovery continues | No sanitizer report; every out-of-range call ends in the handler |
| NVM image fuzzer | Case 2, O5 | Mutated images of regular and EWLF areas, then scan, read, write and commit | No sanitizer report; callbacks never see an address outside the area, and nothing reads outside it without them |
| Fault-injecting callbacks | Case 2, T2.2 | The n-th callback returns an error or different data on each read | Same as above, with errors raised inside transactions |

Also worth doing: a bounded model check (CBMC or Frama-C) of `check_in_data()`, `is_in_range()`, the tracker indexing and the EWLF layout computations used by `ewlf_scan()` and `ewlf_update()`, which carry most of the memory-safety burden. In CI, build with `-Wconversion`, since `offset_wu` is a `uint32_t` derived from a `uintptr_t`. The ASan harness can seed the API fuzzer.
